# Plan A — Pipeline Field Routing Remediation

## Status
`open`

## Part of
`eval-results-remediation` series (standalone phase)

## Dependencies
- None. This plan has no prerequisites.
- Plans B, C, and D from the eval-results-remediation series **depend on this plan completing first**, because they target fields that will live in different extractors after this change.

## Objective
Seven fields are currently owned by the wrong extraction stream. The eval runs exposed concrete extraction failures traceable to misaligned ownership: `outcome_summary` and `actions` live in the scene extractor but belong in progress (where quest context is available); `compendium_npc_update`, `scene_pressure_*`, and `gm_beat` live in the progress extractor but belong in scene (where NPC and location context is fresher and more complete); `failed` lives in the state extractor but is never used there constructively — it should be cut from the LLM schema and derived from narration or rules output instead; `pc_condition_*` stays in state (no merge happening). This plan relocates those fields by updating three Pydantic models, three extractor prompt templates, the merge block in `_run_extraction_pipeline`, two `gm_beat` read sites in `turn.py`, and the `_extract_progress_messages` signature.

## Non-goals
- Does NOT change `apply_delta`, `state.py`, or `pressure.py` logic — only which stream produces which fields.
- Does NOT change prompt wording beyond schema sections and field rule text (no new guard logic — that is Plans B and C).
- Does NOT change the `StateDelta` model — all the fields already exist there; we are only changing which extractor populates them.
- Does NOT change the `StateExtractResult` fields beyond removing `failed`.
- Does NOT touch `pc_condition_*` — staying in state extractor as-is.
- Does NOT add or remove any active_domains entries — domain routing is unchanged.

## Firm decisions

1. **`failed` is cut entirely from the LLM schema.** It was a list of precondition failure strings generated by the state extractor, but the rules engine already knows what failed (via `RulesOutcome.band` and `intent`) and the narrator receives the `band` directive. The field is stored in `events.jsonl` for tracing, but producing it as a separate LLM extraction is wasted tokens and a source of hallucination. The return tuple will pass `[]` for `failed` unconditionally after this change. `turn.py` already handles `failed` being empty gracefully.

2. **`gm_beat` moves to scene extractor.** The scene extractor runs first, has NPC and location freshness, and does not have quest stall age data — but `gm_beat` is a forward-facing story beat instruction, not a quest calculation. The scene extractor is a better fit because it sees the NPC roster, location change, and scene tags before the progress extractor runs. The `deescalate` flag and quest age context (which currently inform `gm_beat` selection in the progress extractor) will be passed into the scene extractor messages function instead.

3. **`actions` and `outcome_summary` move to progress extractor.** These are UI hints and flavor summaries that benefit from quest context (`active_quests`, `quest_ages`). `actions` especially should reflect the current quest state. The scene extractor does not have quest data. This is the correct alignment.

4. **`compendium_npc_update` and `scene_pressure_*` move to scene extractor.** The scene extractor already owns NPC add/remove/update and location change. NPC compendium writes and pressure adds are direct responses to what the scene extractor already sees. Keeping them in progress creates a cross-stream dependency where progress had to re-read NPC context it didn't own.

5. **The `_run_extraction_pipeline` return tuple stays at 6 values.** `(merged_delta, actions, outcome_summary, failed, extraction_event, scene_result)`. The 6th value changes from `progress_result` to `scene_result` so that `turn.py` can read `gm_beat` from it. Both call sites in `turn.py` unpack exactly 6 values and only access `.gm_beat` on the 6th — this is a mechanical substitution with no interface change.

6. **`_extract_scene_messages` receives `deescalate` and `quest_ages` parameters.** These were previously only passed to `_extract_progress_messages` to inform `gm_beat`. After the move, scene needs them. Both parameters already exist in the `_run_extraction_pipeline` call signature. No new data flows.

7. **`_extract_progress_messages` drops `scene_result` parameter.** Currently it receives `scene_result` but only uses it to build an empty `scene_ctx = {}` dict that is never rendered meaningfully. After this change it no longer needs it. The `state_result` parameter stays (items gained/lost context for actions).

After this step it becomes:

```python
class SceneExtractResult(BaseModel):
    scene_tags: list[str] = Field(default_factory=list)
    scene_tagline: str | None = None
    location_change: LocationRef | None = None
    location_description: str | None = None
    npc_add: list[NpcAdd] = Field(default_factory=list)
    npc_remove: list[NpcRemove] = Field(default_factory=list)
    npc_update: list[NpcUpdate] = Field(default_factory=list)
    compendium_npc_update: list[CompendiumNpcUpdate] = Field(
        default_factory=list, max_length=12
    )
    scene_pressure_add: list[ScenePressure] = Field(default_factory=list)
    scene_pressure_remove: list[str] = Field(default_factory=list)
    scene_pressure_update: list[ScenePressure] = Field(default_factory=list)
    gm_beat: GMBeat | None = None

    @field_validator("npc_remove", mode="before")
    @classmethod
    def _coerce_npc_remove(cls, v: Any) -> Any:
        if not v:
            return v
        out: list[Any] = []
        for x in v:
            if isinstance(x, str):
                out.append({"id": x})
            else:
                out.append(x)
        return out

    @field_validator("location_description", mode="before")
    @classmethod
    def _coerce_location_description(cls, v: Any) -> Any:
        if not v:
            return v
        if isinstance(v, str):
            return v
        if isinstance(v, dict):
            return v.get("description", str(v))
        return str(v)
```

**Why:** `SceneExtractResult` gains ownership of NPC compendium writes, scene pressure, and GM beat — the fields that need NPC/location/scene context. It loses `actions` and `outcome_summary` which need quest context instead. The `_coerce_actions` validator is removed with the field.

#### Step 2.1 — Update `_extract_scene_messages` signature and template variables

**File:** `ccya/engine/extraction.py`

**What:** Add `deescalate: bool = False` and `quest_ages: list[dict[str, Any]] | None = None` parameters. Pass both to the scene user template render call.

```python
def _extract_scene_messages(
    env: Environment,
    narration: str,
    state: dict[str, Any],
    *,
    active_domains: list[str],
    rules_outcome: "RulesOutcome | None" = None,
    enable_thinking: bool = False,
    deescalate: bool = False,
    quest_ages: list[dict[str, Any]] | None = None,
) -> list[dict[str, str]]:
    """Build [system, user] messages for stream 1 (scene + UI hints)."""
    pc = state.get("pc") or {}
    location = state.get("location") or {}
    conditions = list(pc.get("conditions") or [])
    known_characters = _known_characters_for_extract(state, compact=True)
    npc_roster = _scene_npc_roster(known_characters)
    present_npcs = list((state.get("scene") or {}).get("present_npcs") or [])
    scene_pressure = list((state.get("scene") or {}).get("scene_pressure") or [])
    active_quests = [
        q for q in (state.get("quests") or []) if q.get("status") == "active"
    ]

    system_text = _render(env, "extract_scene_system.j2", {})
    user_text = _render(
        env,
        "extract_scene_user.j2",
        {
            "narration": narration,
            "pc": pc,
            "location": location,
            "conditions": conditions,
            "npc_roster": npc_roster,
            "present_npcs": present_npcs,
            "rules_outcome": rules_outcome,
            "active_domains": active_domains,
            "scene_pressure": scene_pressure,
            "deescalate": deescalate,
            "quest_ages": quest_ages or [],
            "active_quests": active_quests,
        },
    )
    msgs = [
        {"role": "system", "content": system_text},
        {"role": "user", "content": user_text},
    ]
    if enable_thinking:
        msgs = apply_thinking(msgs, True)
    return msgs
```

**Why:** `deescalate` controls whether pressure should be added or de-escalated. `quest_ages` informs `gm_beat` type selection (stalled quest → pressure/revelation beat). Both were previously passed only to progress; now scene owns GM beat, so it needs them.

**Validation:** Function instantiates without error. Existing callers (Step 2.3) will pass the new kwargs.

#### Step 2.2 — Update `_extract_progress_messages` signature

**File:** `ccya/engine/extraction.py`

**What:** Remove `scene_result` parameter. Remove the NPC compendium and `scene_pressure` reads that used to come from `state`. Progress no longer needs them. `state_result` stays.

```python
def _extract_progress_messages(
    env: Environment,
    narration: str,
    state: dict[str, Any],
    *,
    active_domains: list[str],
    state_result: "StateExtractResult",
    rules_outcome: "RulesOutcome | None" = None,
    enable_thinking: bool = False,
    deescalate: bool = False,
    quest_ages: list[dict[str, Any]] | None = None,
) -> list[dict[str, str]]:
    """Build [system, user] messages for stream 3 (quests + events + actions)."""
    pc = state.get("pc") or {}
    scene = state.get("scene") or {}

    active_quests = [
        q for q in (state.get("quests") or []) if q.get("status") == "active"
    ]
    recent_events = list(scene.get("recent_events") or [])
    world_state = list(scene.get("world_state") or [])

    state_ctx = {
        "items_gained": [it.name for it in state_result.inventory_add],
        "items_lost": [it.id for it in state_result.inventory_remove],
    }

    system_text = _render(env, "extract_progress_system.j2", {})
    user_text = _render(
        env,
        "extract_progress_user.j2",
        {
            "narration": narration,
            "pc": pc,
            "active_quests": active_quests,
            "recent_events": recent_events,
            "world_state": world_state,
            "state_result": state_ctx,
            "rules_outcome": rules_outcome,
            "active_domains": active_domains,
            "quest_threshold_directive": _quest_threshold_directive(active_quests),
            "deescalate": deescalate,
            "quest_ages": quest_ages or [],
        },
    )
    msgs = [
        {"role": "system", "content": system_text},
        {"role": "user", "content": user_text},
    ]
    if enable_thinking:
        msgs = apply_thinking(msgs, True)
    return msgs
```

**Why:** Progress no longer owns `compendium_npc_update`, `scene_pressure`, or `gm_beat`. It no longer needs `known_characters` from `_known_characters_for_extract` (expensive call). It still needs `state_result` for items-gained/lost context for `actions`. `scene_result` parameter is removed entirely — the empty `scene_ctx = {}` that was being built is also removed.

**Validation:** Function instantiates without error. Step 2.3 call site will be updated to match.

New file content:

```
Extract scene state, NPC presence, NPC compendium updates, scene pressure, GM beat, taglines, location, and location description from a narration.
Emit one JSON object matching the schema. No prose, no markdown fences, null for optional fields that don't apply, never omit a key.

## NPC ID format rules

NPC IDs must be `firstname_lastname` only. No titles, roles, or descriptors.
- ✅ `kael_marsh`, `torben_klask`
- ❌ `scarred_soldier`, `doctor_voss`, `the_merchant`
- If only one name is known: `kael` (single token, no decorators)
- When a full name is revealed later: emit `compendium_npc_update` to set the canonical ID and add old ID as alias

IDs are immutable once assigned. Name changes go in the `name` field and `aliases`, not the ID.

## NPC match instruction

Before emitting `compendium_npc_update` to add a new NPC, check the existing compendium list.
If the character is likely the same person referred to differently (e.g. `"scarred soldier"` when `"kael_marsh"` is already in the compendium), use the existing ID and emit an update instead of an add.
Add the old descriptor as an alias. Only emit an add for a genuinely new NPC not present in the current compendium.
If a character is named or re-identified this turn (e.g. you learn the scarred soldier's name is Kael), emit `compendium_npc_update` on the existing ID — do not create a new entry. Add the old descriptor as an alias.
**If the character's name matches an existing compendium NPC (case-insensitive), use their existing ID. Do NOT create a new entry.**

## Output schema

```json
{
  "scene_tags": [],
  "scene_tagline": "",
  "location_change": null,
  "location_description": null,
  "npc_add": [],
  "npc_remove": [],
  "npc_update": [],
  "compendium_npc_update": [],
  "scene_pressure_add": [],
  "scene_pressure_remove": [],
  "scene_pressure_update": [],
  "gm_beat": null
}
```

## Field rules

`scene_tags`: 1-3 lowercase tags from {dialogue, combat, exploration, market, travel, stealth, rest}. Always provide at least one. Include `"game_over"` ONLY if the player character (not an NPC) is confirmed dead this turn. When a scene involves armed/hostile NPCs or physical confrontation, prefer "combat" over "dialogue" even if the player is speaking.

`scene_tagline`: 3-6 word phase. Relevant to story or scene only, not mechanical. Upper case words. Examples: `"Dock Fees Due at Dawn"`, `"The Emperor's Assassin"`.

`location_change`: emit `{"id": "snake_case_id", "name": "Location Name", "description": "1-2 sentences"}` if the player physically moved or the situation has changed significantly. If player has moved away from NPCs, remove them from scene. Null if no change.

`location_description`: Only emit this field if the narration describes a meaningful environmental or atmospheric change to the current location — a shift in lighting, weather, crowd density, physical damage, or emotional register of the space. Do not re-describe unchanged surroundings. If the scene looks and feels the same as before, omit `description` entirely.

`npc_add`: new NPCs entering the scene this turn. Each: `{"id": "snake_case", "notes": "current situation", "name": "Full Name", "title": "Role", "bio": "1-3 sentences"}`. Only include name/title/bio for genuinely new NPCs not in the compendium. Omit name/title/bio for ambient/extra NPCs. If an NPC was previously unnamed (referred to by descriptor), check the compendium roster — if it's the same character, use `npc_update` instead of `npc_add`. **Compendium NPCs are NOT in the scene by default. Emit `npc_add` for any NPC mentioned in the narration that is NOT in `present_npcs`, even if they appear in the compendium roster.**

`npc_remove`: IDs of named NPCs who explicitly left the scene or are no longer in proximity. Each: `{"id": "existing_id", "last_seen_state": "1-sentence description of what they were last seen doing"}`. **Only remove NPCs when the narration clearly states or implies they left.** Do NOT remove NPCs just because the scene shifted focus or the narration stopped mentioning them. Do NOT remove allies, family, or key characters who follow the player. When in doubt, keep them in the scene.

`npc_update`: existing scene NPCs whose notes changed this turn. Each: `{"id": "existing_id", "notes": "updated situation"}`. Name/title/bio only change when new information arrives. If the narration mentions an NPC who is already in the scene, you MUST emit an `npc_update` for them even if only updating notes.

`compendium_npc_update`: NPC records to create or update based on genuinely new durable info (allegiance changed, died, new name learned, relationship revealed). Each: `{"id": "npc_id", "name": "optional", "title": "optional", "bio": "updated 1-3 sentence durable identity"}`. Don't re-emit NPCs whose info didn't change. If the narration describes an NPC as killed, mortally wounded, captured, or permanently removed: emit `compendium_npc_update` with `bio` recording their fate in one sentence.

`scene_pressure_add`: Add a `scene_pressure` entry when the narration introduces a time-sensitive threat, pursuit, hazard, or countdown. Set `urgency` based on immediacy: "immediate" if it must be addressed this turn, "building" if it escalates over 2-4 turns, "background" for ambient threat. Set `max_turns` to an explicit fiction-grounded expiry if the narration implies a hard deadline. Do NOT add lore or permanent world facts; those go in `world_state`. Each: `{"id": "snake_case_id", "text": "Threat description", "urgency": "immediate|building|background", "turn_added": 0, "max_turns": null}`.

`scene_pressure_remove`: IDs of pressures now resolved — the fire is out, the guards were evaded, the bomb was defused.

`scene_pressure_update`: Changes to existing pressure text or urgency. Each: `{"id": "existing_pressure_id", "text": "updated text", "urgency": "immediate|building|background"}`.

## De-escalation

When `deescalate` is true (shown in user prompt): do NOT emit `scene_pressure_add`. Emit `scene_pressure_update` to downgrade urgency (`immediate → building`, `building → background`). If fully resolved, emit `scene_pressure_remove`. Pair with a `breathing_room` GM beat.

## GM Beat (gm_beat)

**IMPORTANT: `type` vs `surface_as` are different fields.**
- `type` is the beat category: `complication`, `revelation`, `opportunity`, `breathing_room`, `pressure`.
- `surface_as` is how the beat is presented: `ambient`, `event`, or `npc_behavior`.
- **Common mistake:** Do NOT set `type: "ambient"`. `ambient` is a `surface_as` value.

After extracting this turn's scene changes, decide whether to emit a forward-facing story beat for the NEXT turn.

Emit `null` if:
- There are 3+ active `scene_pressure` entries (don't pile on)
- `deescalate` is true (use `breathing_room` GM beat instead — see above)
- The player is in a critical resolution moment (final quest objective in reach)
- Nothing meaningful has changed in NPC, scene, or location state to react to

Emit a beat when:
- `pc.momentum` >= +2: emit `complication` to raise stakes
- `pc.momentum` <= -2: emit `opportunity` or `breathing_room`
- A quest has been stalled for 3+ turns (shown in quest_ages): emit `pressure` or `revelation`
- An NPC with unknown or shifting allegiance is present: emit `revelation`

Beat instruction rules:
- 1-2 sentences. Concrete, not vague.
- BAD: "Something bad happens to the player." GOOD: "A contact the player trusted has been seen meeting with the opposing faction at the dockside inn."
- BAD: "Give the player a break." GOOD: "The player spots a satchel left behind by a fleeing guard — it contains a vial and a partial map."

`surface_as` guidance:
- `ambient`: low-stakes background texture. Used for `breathing_room` and most `revelation` beats.
- `event`: something the player can directly interact with. Used for `opportunity` and `pressure`.
- `npc_behavior`: a present NPC shifts their demeanor, loyalty signal, or body language. Best for `revelation` and `complication`.

## NPC scene cap

No more than 8 named NPCs in a scene. If the narration introduces a 9th, the oldest/least relevant named NPC should be removed (goes into `npc_remove`). Ambient NPCs don't count toward the cap. Allies, family, and key characters should be assumed to follow the player when he moves — don't remove them on location change. **NPC removal should only happen for one of two reasons: (1) the narration clearly shows the NPC left, or (2) the scene cap is exceeded and you must evict the least relevant NPC.**

## State-presence rule

Sections not shown in the user prompt still exist in the live game state — absence is not removal. Only infer changes that are explicit.
```

The de-escalation and GM beat rules are transplanted from the progress system prompt (they will be removed from there in Step 4.3).

Add field rules after the existing `recent_events_remove` rules:

```
`actions`: exactly 4 distinct player choices, ~10 words each, drawn from THIS turn's narration AND the current quest state. Structure: two choices should offer distinct avenues related to the current quest (if any), one should involve an NPC who is present in the scene, and one should be an exploration/environmental action or freeform option. Weight toward the player's strongest stat (don't mention stat), quest objectives, and motivations. Each one should move the plot forward substantially in a different direction. Examples: "Aim for the chest and fire", "Sneak past the guards and search the room", "Convince the guard to let you pass", "Create a diversion to slip past the guards". Bias to bold, good storytelling choices. Ground these in the active quest objectives shown above.

`outcome_summary`: one or two short sentences: what just happened in flavor terms, showing narrative impact on player, npcs, scene, and quest progress. For failures: describe what went wrong narratively and what quest objective remains blocked. Examples: `"You successfully picklock the padlock and enter the vault."`, `"The guard spots you and raises the alarm — the delivery remains unconfirmed."`.
```

Also remove the `## Rules-outcome guidance (for objective resolution)` section's reference to `gm_beat` if present.

**Why:** Progress loses NPC compendium, pressure, and GM beat. It gains `actions` (benefits from quest context) and `outcome_summary` (benefits from quest context for failure descriptions).

### Risks

1. **`extraction_event["progress"]["output"]` serializes old fields.** After the model change, `progress_result.model_dump()` will no longer include `compendium_npc_update`, `scene_pressure_*`, or `gm_beat`. The turn viewer and judge that read these keys from `extraction_event["progress"]` will see them absent. They will need to read from `extraction_event["scene"]` instead. This is expected and correct — but if the judge's `universal_asserts.py` hardcodes `extraction_event["progress"]["output"]["gm_beat"]` it will start returning KeyError. Check and update the judge after this plan ships. (Noted as a dependency for Plan E.)

2. **`_known_characters_for_extract` was called in `_extract_progress_messages`.** Removing it saves an expensive call per turn. Verify it is still called in `_extract_scene_messages` (it is — for `npc_roster`) so the compendium data still reaches the LLM.

3. **`deescalate` logic duplication.** Both scene and progress currently receive `deescalate`. After this plan, only scene needs it for pressure/beat. Progress still receives it for `quest_threshold_directive` context. This is fine — it's a bool, not expensive to pass to both. Do not remove it from the progress call.

4. **Stale `extraction_event` keys in eval traces.** Existing eval runs store `gm_beat` under `extraction["progress"]["output"]`. Any eval judge assertions that check that path will need updating after this plan. Flag for Plan E author.
