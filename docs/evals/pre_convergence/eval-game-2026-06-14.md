## 1. Pydantic validation — `inventory_change_reason` missing

**Severity:** WARN — retry succeeds, no data loss. Costs tokens + latency.

**Root cause:** The prompt already has a "Reason field" section (`extract_state_system.j2:43-45`) saying it's required, but the LLM still omits it when inventory changes are present. The retry mechanism works (succeeds on attempt 2), so this is a compliance issue, not a data loss issue.

**Occurrences:** Turns 8, 11, 18, 20 — all single retries (attempt 1/2), all succeeded on retry.

### Proposed fix

**Option A — Strengthen the prompt (recommended)**

```
Before (extract_state_system.j2:43-45):
## Reason field

State why inventory changed this turn. Be very concise — a short phrase, not a sentence. Examples: "Player picked up from ground", "X NPC gave it to player", "Player lost pistol in a brawl", "Tool was destroyed by electric surge". If multiple items were added or removed, explain all changes in one reason covering both adds and removes together. Required whenever `inventory_add` or `inventory_remove` is non-empty. Not required for `inventory_update` or `pc_condition_*` changes alone.

After:
## Reason field — REQUIRED

`inventory_change_reason` is REQUIRED whenever `inventory_add`, `inventory_remove`, or `inventory_update` is non-empty. Omitting it when inventory changes exist will cause the output to be rejected. State why inventory changed this turn in one short phrase. Examples: "Player picked up from ground", "X NPC gave it to player", "Player lost pistol in a brawl". Multiple items → one reason covering all changes. NOT required for `pc_condition_*` alone.
```

**Option B — Coerce in `_parse_stream_result`**
Add a pre-validation step in `extraction.py` that injects `"Inventory changed this turn"` when inventory fields are present but `inventory_change_reason` is missing. Tradeoff: hides LLM compliance failure, loses semantic detail.

**Option C — Make validator conditional**
Change the Pydantic validator to auto-generate a default reason instead of rejecting. Tradeoff: same as B.

**Directive and spiral overrides** replace the phase table above:

- **Breathe** — allowed: `breathing_room`, `opportunity`, `revelation`, `callback`

## 4. `thread_lifecycle` — Unknown thread ID `clear_the_road_toughs`

**Severity:** WARN — pre-existing bug, not caused by new code.

**Root cause:** A thread was created, then something (sanitizer? arc resolution?) removed it from state, but the LLM's context window still contains it in prior history. Subsequent turns' storyteller LLM still references it because it's in the `prior_history` or `recent_turns` sections of the user prompt.

**Occurrences:** Every turn from T7 onward.

### Proposed fix

**Option A — Track evicted thread IDs and suppress in context (recommended)**
When a thread is removed from state, track its ID. In subsequent turns, filter out references to evicted threads from `prior_history` and `recent_turns` sections of the user prompt. Tradeoff: modifies prompt rendering, may lose narrative continuity.

**Option B — Graceful handling in thread sanitizer**
When a thread update references a non-existent thread, log a warning but silently skip it rather than failing. Tradeoff: masks the root cause (LLM still generating invalid references).

**Option C — Fix thread eviction in state machine**
Ensure threads are properly archived/removed from all state references (including `completed_threads` cleanup) so they don't persist in state snapshots. Tradeoff: may require changes to thread lifecycle logic.

**Recommendation:** A + B combined. Track evicted thread IDs and filter them from context rendering (A), AND silently skip invalid thread references in the sanitizer (B). This addresses both the symptom (LLM references dead threads) and the cause (context still contains them).

## 6. `tension_monotonicity` — Tension delta doesn't match phase expectations

**Severity:** WARN — pre-existing ruling prompt compliance issue.

**Root cause:** The ruling LLM's `tension_delta` doesn't always align with what the phase machine expects. CRISIS with `de-escalates` and BREATHER with `escalates` are flagged. This is a ruling prompt compliance issue.

**Occurrences:** Every turn — CRISIS with `de-escalates` (multiple), BREATHER with `escalates` (multiple).

### Proposed fix

**Option A — Relax the checker (recommended)**
Allow CRISIS to have `de-escalates` when `outcome_hint == "transition"` (player is actively resolving/leaving). Allow BREATHER to have `escalates` when there are urgent threads. Tradeoff: reduces checker strictness, may hide genuine ruling issues.

```
Before (ccya/ev/checkers/tension_monotonicity.py:50-57):
# Phase consistency: de-escalates should not appear in CRISIS
# (CRISIS should have escalates or maintains)
if phase == "CRISIS" and tension_delta == "de-escalates":
    findings.append({
        "turn": turn_no,
        "check": "crisis_tension",
        "detail": "CRISIS phase with tension_delta=de-escalates (expected escalates or maintains)",
    })

After:
# Phase consistency: de-escalates in CRISIS is allowed when transitioning out
# (player is actively resolving or leaving the scene)
pc = extract_field(ev, "pacing_context") or {}
outcome_hint = pc.get("outcome_hint", "")
if phase == "CRISIS" and tension_delta == "de-escalates" and outcome_hint != "transition":
    findings.append({
        "turn": turn_no,
        "check": "crisis_tension",
        "detail": "CRISIS phase with tension_delta=de-escalates (expected escalates or maintains, unless transitioning)",
    })
```

**Option B — Strengthen the ruling prompt**

```
Before (ruling_system.j2, tension delta section):
## Tension delta

- `escalates`: Player is attacking, confronting, pushing forward aggressively — tension is rising.
- `maintains`: Player is acting with normal intent — no significant change in tension.
- `de-escalates`: Player is retreating, hiding, calming, avoiding conflict — tension is dropping.

After:
## Tension delta

- `escalates`: Player is attacking, confronting, pushing forward aggressively — tension is rising.
- `maintains`: Player is acting with normal intent — no significant change in tension.
- `de-escalates`: Player is retreating, hiding, calming, avoiding conflict — tension is dropping.

**Phase expectations:**
- CRISIS: tension should escalate or maintain (player is in the climax). De-escalate only when transitioning out.
- BREATHER: tension should maintain or de-escalate (scene is recovering). Escalate only if a new urgent thread emerges.
- SETUP/RISING/RESOLUTION: tension follows player intent naturally.
```

**Option C — Decouple tension from phase expectations**
Remove the monotonicity check entirely. Tension is a soft signal from the ruling LLM, not a hard constraint. Tradeoff: loses a useful validation signal.

**Recommendation:** A + B. Relax the checker to allow legitimate edge cases (A), AND strengthen the ruling prompt to set clearer expectations (B). This addresses both the false positives and the root cause.
