## Current State — What Exists

### Pacing Signals: Three Redundant Age Trackers

`turn.py::_compute_ages()` produces three independent age counters written to `TurnContext._ages`:

- `scene_age` — turns in the current scene (since `scene.turn_entered`)
- `location_age` — turns at the current location (since `scene.location_entered_turn`)
- `combat_age` — turns since `scene.combat_started_turn` (set when scene tags contain `"combat"`)

A helper `_inject_location_pressure()` exists (defined but never called) that would produce `Location Pressure` and `Location Imperative` from `location_age`. Only `Combat Fatigue` (combat_age ≥ 3, secondary append) is actually emitted by `_compute_narration_directive()`. The narrator prompt in `narrate_system.j2` defines `Location Imperative` and `Location Pressure` as separate static directive strings — they are dead in practice, never generated by the engine, but still consuming prompt tokens and creating confusion around intent.

### Pacing Signals: Beat-Locked Relief

`_compute_pacing_context()` sets `beat_locked = True` when `momentum <= config.momentum_floor` (-3). This fires a `"Resolve a Threat"` directive. `beat_locked` also injects a fresh `breathing_room` beat post-extraction (line 1285). However, `pending_gm_beat` is zeroed unconditionally at line 1149 after narration, before the storyteller extraction runs. Any storyteller-written beat meant to carry over with `beat_expires_turn` is destroyed — only the re-injected `breathing_room` beat from `beat_locked` survives because it's re-created after the clear, not because of proper persistence.

There is no `consecutive_pressure_turns` counter. The engine cannot detect a player who has received three successive `Pressure` or `Overwhelm` directives without any thread advancement — a common sign the player is stuck.

### Band History: Not Tracked

`state["meta"]` has no rolling band log. Three consecutive `fail`/`crit_fail` rolls are indistinguishable from a successful turn at the engine level — momentum is a lagging aggregate, not a sequential signal.

### Arc Thread Creation: No Deduplication by Concept

`_apply_thread_signals()` checks thread creation against `existing_ids` (exact `id` string match). Two threads with semantically identical tensions but different IDs both pass the gate. The storyteller prompt in `storytell_system.j2` has no instruction to check for conceptual overlap with existing threads before emitting `thread_add`.

### Primary Thread: Not Designated

There is no mechanism to surface a single "most important active thread" to the narrator or storyteller. The narrator receives all active threads with equal weight.

### GMB Extenders: Mood

`Mood` is referenced in design discussion but is **absent from both `narrate_system.j2` and `storytell_system.j2`**. It does not appear in the narrator user prompt template context. It is inert.

### ARC_UPDATE: `thematic_question` and `pc_drive` Not Exposed

`_ALLOWED_NARRATOR_ARC_KEYS` in `turn.py` permits `thematic_question` and `pc_drive` updates, but the narrator system prompt's `<<<ARC_UPDATE_START>>>` JSON schema example only shows `discovered_truths` and `visible_goal`. The LLM does not know it can emit `thematic_question`.

### `recently_left` NPC Tracking

`scene.recently_left` and `scene.recently_left_turns` track NPCs that departed the scene. `npc_roster.py::build_npc_roster()` uses this to tag NPCs as `JUST_LEFT` in narrator context. The `narrate_system.j2` `## NPCs in scene` section has dedicated `JUST_LEFT` handling rules. The signal is low-value and adds state complexity.

### Nearby Locations: Dead Feature

`narrate_user.j2` line 44 conditionally shows a "Nearby Locations" section when `location_age >= 3`. However, no packs define any locations in their scenario (`pack_locations` from `_app_mod._active_pack.scenario.locations` is always empty). This feature can never fire — it is dead code.

### Problems with Current State

- `location_age`, `combat_age`, and `scene_age` track the same concept; only `combat_age` actually drives a directive (`Combat Fatigue`). `location_age` feeds a dead function (`_inject_location_pressure()` is never called) AND a dead template section (nearby locations). `scene_age` is computed into prompt context but unused in directive logic.
- `beat_locked` relief is conceptually correct but mechanically broken: the unconditional `pending_gm_beat = None` clear after narration destroys any carried beat before it reaches the next turn.
- No consecutive-pressure counter means the engine cannot distinguish a tense-but-progressing sequence from a stuck loop.
- Thread deduplication operates on ID strings only; semantic duplicates are not detected at creation time.
- `Mood` is a dead field — adds no signal.
- `thematic_question` is silently updatable in engine but the narrator is never told.
- `recently_left` + `JUST_LEFT` machinery adds state and prompt complexity for minimal storytelling value.

## Target State — What It Becomes

### Core Changes

#### 1. Unified `scene_age` — Single Staleness Signal, Many Inputs → Multi-Faceted Output

Replace `location_age`, `combat_age`, and `scene_age` with a single `scene_age` integer in `state["scene"]`. `scene_age` is computed as turns elapsed since `scene.turn_entered`. It increments every turn regardless of location or combat status.

**Directive interaction (many signal inputs → one multi-faceted output):** The directive system (`_compute_narration_directive`) already works as a priority stack with multiple independent signals feeding into it: narrative_velocity, urgency counts from scene threads, and threat ages all act as separate inputs that produce the highest-priority directive. `scene_age` joins this signal set rather than replacing combat_age via weighted thresholds. When `"combat"` is in the scene tags, an additive boost (+2) is applied to `scene_age` before threshold comparison — effectively making the scene feel older/faster during combat without introducing a second age variable or complex weighting math.

**Combat boost implementation:** The +2 combat boost is pre-computed into the ages dict as `"effective_scene_age"` (computed in `_compute_pacing_context` or `_narrate_setup` before calling `_compute_narration_directive`). This way `_compute_narration_directive` only reads `ages.get("effective_scene_age", 0)` — no new parameters needed, consistent with how the function already reads from ages dict for other signals.

**Thresholds:** Fixed comparison points against `effective_scene_age` (not raw scene_age):
- Intermediate (`Scene Pressure`): effective age ≥ 3 → non-combat triggers at turn 3, combat triggers at turn 1
- High (`Scene Imperative`): effective age ≥ 5 → non-combat triggers at turn 5, combat triggers at turn 3

Combat scenes reach pressure thresholds ~2 turns earlier than non-combat because the +2 boost makes `effective_scene_age = scene_age + 2`. This reflects the need to press faster when danger is present.

These two directives subsume all three legacy directives (`Location Pressure`, `Location Imperative`, `Combat Fatigue`). The existing priority stack handles resolution — higher-priority directives short-circuit lower ones.

**Reset condition:** `scene_age` resets when `scene.turn_entered` is updated — i.e., when the scene extractor emits a `location_change`. Intra-scene pivots (new NPC arrives, confrontation changes character) do NOT reset `scene_age`. Scene age is location-scoped.

**Narrator prompt impact:** Remove the `Location Pressure`, `Location Imperative`, and `Combat Fatigue` directive definitions from `narrate_system.j2`. Add `Scene Pressure` and `Scene Imperative` definitions. Estimated net reduction: ~80 tokens.

**Remove nearby locations section entirely:** Delete the `{% if world_locations and ages and ages.get('location_age', 0) >= 3 %}` block from `narrate_user.j2` (line 44-47). No packs define any locations so this feature never fires. Also remove `world_locations` from `_narrate_messages()` call in turn.py line 999 and the parameter from `narrate.py::build_narrate_messages()`.

#### 2. `pending_gm_beat` Carryover Fix

Remove the unconditional `state["meta"]["pending_gm_beat"] = None` lines from `run_turn`. There are two locations to address:

- **Line ~1149:** Unconditional clear after narration, before storytell extraction runs (destroys any carried beat).
- **Lines ~1198-1200:** Else block that clears the beat when storytell emits null or no new `gm_beat` — this defeats the carryover fix from line 1149 because common turns where no GM action is warranted will re-clear any previously carried beat.

The only beat lifecycle management should be:

- **Written:** after storytell extraction, if `StorytellerResult.gm_beat` is non-null, write to `state["meta"]["pending_gm_beat"]` with `beat_expires_turn = turn_no + 2`.
- **Consumed (read-gated):** `_narrate_setup()` reads `pending_gm_beat` and passes it to the narrator only if `turn_no <= beat_expires_turn`.
- **Cleared:** only when a new beat is written (replaces), or when `turn_no > beat_expires_turn` at read-gate time.

The beat now persists across turns until it expires or is replaced, as designed.

#### 3. Consecutive Pressure Counter + Relief Trigger

**`state["meta"]["consecutive_pressure_turns"]`:** Integer counter, updated at end-of-turn using a two-pass approach: the directive value is already baked into `pacing_ctx` from earlier in the turn (before storytelling runs), and thread_advance knowledge only becomes available after `_run_extraction_pipeline()` completes. At end of turn, if pacing_ctx's directive was `Pressure` or `Overwhelm` AND storyteller result had empty `thread_advance` → increment counter to 0 whenever the stored directive from that turn was not `Pressure`/`Overwhelm`, or when any thread was advanced during storytelling.

**Relief trigger:** `beat_locked` fires when **either**:
- `consecutive_pressure_turns >= config.consecutive_pressure_threshold` (default 3), OR
- `momentum <= config.momentum_floor` (-3) — existing behavior preserved

This dual-trigger approach ensures pacing relief is available through either signal path: the new counter catches stuck players who are progressing but receiving repeated pressure directives, while momentum floor provides an immediate safety valve for rock-bottom states. The old single-trigger system had no consecutive-pressure detection; this adds it without removing the proven momentum fallback.

`beat_locked` continues to set directive to a breathing_room-favoring value (existing behavior in storytell guidance).

#### 4. Arc Thread Canonical Key Deduplication

`ArcThread` gains a new optional field `key: str | None`. The `key` is a 2–4 token snake_case canonical concept label (e.g. `"lira_betrayal"`, `"hull_breach"`). It is emitted by the storyteller in `thread_add`.

**Storyteller instruction:** Instruct the LLM to generate keys using structured conventions (`subject_action` or `location_event` format, lowercase snake_case) to prevent drift across turns. Before emitting `thread_add`, check active and latent thread summaries for conceptual overlap; if overlap exists, emit `null` instead of creating a duplicate.

**Python-side dedup gate (at thread_add point in run_turn):**
1. Existing `id` collision check (unchanged).
2. New: Check `thread_add.key` against `{t.key for t in arc.threads if t.key}` using token-overlap scoring (same pattern as `_fuzzy_match_inventory` at inventory.py — set intersection of tokens divided by max length). Uses 70% threshold rather than the 60% used for inventory matching, justified because thread keys are short canonical labels where false positives would be more damaging than with longer inventory names. If similarity ≥ 70% → auto-merge by updating the existing thread's summary and tags rather than rejecting outright. Log INFO at merge point noting which threads were merged.
3. If key collides but fuzzy match is below threshold: reject `thread_add`, log `WARNING thread_add.key_collision`.

**Dedup placement:** The key dedup check should happen before the scope gate (`elif _scope == "scene": pass`), so that scene-scoped threads also get key-based deduplication. Otherwise all scene-scoped threads bypass the new dedup entirely.

**Auto-merge rationale:** Rejecting new threads silently causes story tensions to go untracked entirely. Auto-merging preserves the new tension while avoiding duplicate entries, which is safer than either pure rejection or blind acceptance of every new thread.

#### 5. `thematic_question` in Narrator ARC_UPDATE

The narrator system prompt's `<<<ARC_UPDATE_START>>>` JSON schema example is updated to include `thematic_question` as an allowed key. The rule remains: only emit when the turn's narration has materially shifted the story's emotional register.

The `_ALLOWED_NARRATOR_ARC_KEYS` set in `turn.py` already includes `thematic_question`; no engine change needed.

#### 6. Remove `recently_left` and `JUST_LEFT`

`scene.recently_left` and `scene.recently_left_turns` are removed from state. The decay logic at turn.py lines 1422-1430 is deleted. NPCs that left the scene simply become part of the compendium/known pool without special tagging (presence field transitions present→known automatically on location change). The `## NPCs in scene` section in `narrate_system.j2` that describes `JUST_LEFT` behavior is removed.

**Non-backward-compat:** This is a non-BC change — no migration path for saved games containing these fields. Stale keys will be silently ignored on load.

#### 7. Drop Mood

No `Mood` field is added anywhere. No design action. Confirmed inert — the only reference to `mood` outside this doc is in `generate_pack_user_wb.j2` which uses a pack-level `mood_note` variable for campaign generation, not turn-time pacing.

|---|---|---|

| Scene age resets on location change only | `scene_age` tied to `scene.turn_entered`; intra-scene pivots do not reset | Location change is the only unambiguous signal that stale-scene pressure is resolved |
| Remove unconditional `pending_gm_beat = None` | Beat clears only at write (replace) or expiry read-gate | Fixes carryover bug; aligns with documented intent |
| `consecutive_pressure_turns` in `state["meta"]` | Persisted across turns, reset on thread advance or non-pressure directive | Momentum is lagging aggregate; sequential pressure needs a sequential counter |

## Complexity Analysis

**What gets removed (~150-170 lines of code impact):**
- `_inject_location_pressure()` function entirely (turn.py ~24 lines) — dead code removal ✓
- `location_age` computation in _compute_ages() (3 lines) ✓  
- `combat_age` computation in _compute_ages() (~5 lines including conditional logic) ✓
- Config fields: `location_pressure_at`, `location_imperative_at` (config.py 2 lines) ✓
- Nearby locations section from narrate_user.j2 + world_locations param removal (~10 lines across turn.py and narrate.py) ✓
- `recently_left` population in npcs.py (~10 lines) ✓
- `recently_left` decay logic in turn.py (~9 lines) ✓
- `recently_left` reads in _narrate_messages() call sites (~3 locations, ~6 lines total) ✓
- JUST_LEFT handling in npc_roster.py (~25 lines including enum value, sorting priority, and function param change) ✓
- JUST_LEFT section removal from narrate_system.j2 (~8 template lines) ✓

**What gets added (~70-90 lines of code impact):**
- `consecutive_pressure_turns` counter with two-pass end-of-turn update logic (stored directive from pacing context + post-extraction thread_advance check) (~12-18 lines)
- Pre-computed `"effective_scene_age"` in ages dict with combat boost before calling _compute_narration_directive (~4-6 lines — simple conditional addition to scene_age value passed into existing ages dict)
- ArcThread.key field + auto-merge validation/normalization logic at thread_add point (before scope gate, so scene-scoped threads also get deduped) (~20-30 lines including token-overlap similarity comparison and merge handling using pattern from inventory.py)

**Net estimate: ~−75 to −95 lines of code overall, with reduced cognitive complexity.** The new signal inputs approach for directives reuses the existing priority stack rather than adding weighted math. Pre-computed effective_scene_age in ages dict avoids changing _compute_narration_directive's signature. Auto-merge on key collision is more robust than rejection using proven token-overlap pattern from inventory.py. Dual-trigger relief (consecutive pressure OR momentum floor) covers both stuck-player and rock-bottom scenarios without needing band history windowing. Storyteller prompt cognitive load increases slightly (~20 tokens for structured key generation instruction), but this trades one-time complexity investment against ongoing duplicate thread management costs.
