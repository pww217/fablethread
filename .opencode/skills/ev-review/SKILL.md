Purpose: Focused deep-dive on a specific mechanic, turn range, or fix validation. Not a full rubric pass — that's `ev-run`'s job. The user specifies what to examine; the skill delivers a customized report based on that request.

**Sequential work:** One mechanic at a time. One issue at a time when investigating bugs. Do not pull multiple mechanics or issues into context simultaneously.

**Eval tickets as memory:** If new issues warrant tracking, create ONE `E-` ticket per review session. The review report lives within the eval ticket, linking to the eval/save examined. Update the ticket continuously — it is the long-term memory for this work.

**Checkers are bellwethers, not verdicts.** A passed checker means something *might* be healthy. A failed checker means something *might* be unhealthy. Neither is proof. Always pair checker results with subjective examination — pull live data from runs and examine it directly. Use checkers as input, not as the basis for conclusions.

## Sources

- **Eval run dir:** `evals/runs/<group>/<run>/` (has `run-meta.yaml`, `report.md` auto-generated by `ev.py` with `--auto-report` or `auto_report: true` in `ev.yaml`)
- **Player save dir:** `saves/<name>/` (no metadata, created by web UI)
- **Group-level:** `evals/runs/<group>/REPORT.md` (consolidated report across multiple runs)
- **Roadmap:** `roadmap/bugs/` — scan for `testing` items
- **Eval tickets:** `roadmap/evals/` — prior eval findings and context

## Prerequisites

Before analyzing, read:
- `docs/ev/COMMANDS.md` — understand what each command does
- `docs/ev/CHECKERS.md` — understand checker definitions
- Relevant architectural docs from `docs/architecture/` for the mechanic being examined

## Step 1: Context Assessment

If the user explicitly asks to review against recent commits, inspect what changed:

```bash
# Find the prior eval group in evals/runs/ (the newest one before the current group)
# Extract the SHA from the group directory name:
#   evals/runs/2026-06-27_0.30.0-28-g0d8013d5_0d8013d/
#                                                 ^^^^^^^
#                                                 prior SHA
# Format: YYYY-MM-DD_{tag}_{sha:8}_{sha:8} — the last 8-char hex is the SHA
git log --oneline <prior_sha>..<current_sha> -- ccya/
```

**Scope:** Only `ccya/` folder changes (engine code, prompts, templates). Ignore:
- `evals/` — eval tooling
- `docs/` — documentation
- `roadmap/` — planning
- `plans/` — planning
- `scripts/` — developer tooling

**Focus areas (higher risk for regressions):**
- `ccya/prompts/` — prompt changes can affect extraction, ruling, narrate
- `ccya/engine/` — engine logic changes can affect pacing, convergence, phase transitions
- `ccya/models.py` — state model changes can affect serialization/checkers

Report a summary of changed files and their areas in the report.

If the user did NOT ask for a commit review, skip this step.

## Step 2: Testing Item Review

If the user asks to validate a fix for a bug in `testing` status, or if the review is about a specific fix:

For each bug with `status: testing` in the roadmap that matches the mechanic(s) being reviewed:

1. **Find relevant run(s)** — identify which eval run(s) are relevant to the bug
2. **Run targeted checkers** — use `ev.py check` with appropriate checkers against the relevant run(s) (bellwethers only)
3. **Subjective examination** — pull live data from the relevant run(s) and examine it directly. Do not rely on checker pass/fail as proof of correctness.
4. **Assess result:**
   - If bug behavior is absent or fixed → update status to `done`, add `completed: YYYY-MM-DD` to the bug file, call the `ticket` skill, run `make roadmap`
   - If bug behavior still present → update status back to `up-next`, note regression in report
5. **No bug file update** if the testing item is a feature (not a bug) — just note in report whether it's confirmed working

If the user did NOT ask for fix validation, skip this step.

## Step 3: Targeted Mechanic Analysis

Run targeted checkers and commands for the specific mechanic(s) requested:

```bash
# Full dump of a specific turn
.venv/bin/python scripts/debug/ev.py turn <N> --save-dir <path>

# Roll math and beat timing
.venv/bin/python scripts/debug/ev.py mechanics <N> --dice --pacing --save-dir <path>

# Thread lifecycle analysis
.venv/bin/python scripts/debug/ev.py threads --summary --save-dir <path>

# Track a state field across turns
.venv/bin/python scripts/debug/ev.py trace <field.path> --save-dir <path>

# Run specific checkers for the mechanic
.venv/bin/python scripts/debug/ev.py check --checker <checker-name> --save-dir <path>
```

**Focus on:**
- The specific mechanic(s) requested by the user
- Relevant turn ranges (e.g., turns 1-5 for early game, turns 15-25 for late game)
- Comparisons to prior eval runs if available
- Run ONLY the commands relevant to the request. Do not run the full rubric. Do not analyze mechanics the user did not ask about.

## Step 4: Write Focused Report

Write a focused, customized report based on the user's request. The report lives within an `E-` ticket, linking to the eval/save examined.

### Sections (tailored to the user's request):
1. **Request** — what the user asked to examine
2. **Sources examined** — which runs, which commands, which turns
3. **Findings** — detailed analysis of the specific mechanic(s) via subjective examination
4. **Comparisons** — vs. prior runs if relevant
5. **Recommendations** — what to investigate or fix next

## New Tickets

If new issues warrant tracking, create ONE `E-` ticket per review session (not per finding). Include:
- Review context and what was examined
- Evidence paths (eval group, save dir, commands run)
- Mechanic focus
- All findings in the ticket body

The review report lives within the eval ticket, linking to the eval/save examined.

## What NOT to Do

- Do not run the full rubric — that's `ev-run`'s job
- Do not generate per-run `report.md` files — those are auto-generated by `ev.py` with `--auto-report`
- Do not overwrite existing bug files — create new slugs for new issues
- Do not analyze commits outside `ccya/` folder for regression risk (unless explicitly asked)
- Do not review mechanics the user did not request
- Do not pull multiple mechanics or issues into context at once — work sequentially
- Do not rely on checkers as proof of correctness — they are bellwethers only
