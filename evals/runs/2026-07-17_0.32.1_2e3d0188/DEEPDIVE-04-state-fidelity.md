## 4.1 LLM Drift in Ruling/Narration vs. State Fidelity

**Architecture docs to reference:**
- `docs/architecture/state-models.md` — WorldState (root model), typed mutators, extraction models
- `docs/architecture/step2c-record.md` — engine-driven arc, validation edge cases
- `docs/architecture/cross-module-contracts.md` — error propagation path, extraction field routing
- `docs/architecture/prompt-variable-contracts.md` — prompt variable contracts

**Hypothesis:** If the ruling/narration doc finds drift or inconsistency, that could propagate to the Record extractor, which affects how urgency is assigned, which affects the sanitizer, which affects convergence. A drift cascade.

**Data sources:**
- `evals/runs/2026-07-17_0.32.1_2e3d0188/ruling_narration_and_npcs.md` — existing ruling/narration findings
- `evals/runs/2026-07-17_0.32.1_2e3d0188/state.md` — state summary
- Events: `kind: "narrate"` and `kind: "extract"` across all 5 runs
- `ccya/engine/thread_sanitizer.py` — sanitizer drift detection

**Investigation steps:**
1. What drift patterns does the ruling/narration doc already identify?
2. Does drift correlate with convergence anomalies? (e.g., runs with high drift have lower convergence)
3. Is there a propagation path: drift → extract errors → sanitizer confusion → convergence dampening?
4. Can drift be measured quantitatively (e.g., state consistency score per turn)?
5. **Gap:** Check validation edge cases — step2c-record.md:275-283. 8 edge cases including unknown thread ID, duplicate thread ID, progress dedup rejection. Do any of these edge cases trigger more frequently in late turns, indicating drift?
6. **Gap:** Check error propagation — cross-module-contracts.md:9. LLM failure in extraction → typed LlmcError → caught by server middleware → persisted to server_errors.jsonl. Are there extraction errors that correlate with convergence anomalies?

**Findings:**

### 4.1.1 Drift patterns identified in ruling/narration doc

The ruling/narration doc identifies several drift patterns that propagate downstream:

1. **Beat-to-narration disconnect (8-16% alignment):** Beats generated by World step are not woven into narration. This means the Narrate prompt's `pending_gm_beat` is essentially ignored, so the Narrator makes rulings based on incomplete scene context. This is a **ruling fidelity** issue — the LLM decides dice checks without knowing about the GM's intended beat, leading to rulings that don't align with the intended scene direction.

2. **Thread one-directionality (all advancement, no setbacks):** Record extractor emits `major_update_signal: advancement` regardless of roll band. This means thread urgency/progress state drifts upward — threads appear to be progressing even when the player is failing. The sanitizer receives these updates but has no downward correction signal.

3. **Narrative loops (noir-1930s T10-T17):** Same scenes, same NPCs, same actions repeating. This is a **state fidelity** issue — the world state is not evolving because beats aren't driving new developments and setbacks aren't being recorded.

### 4.1.2 Drift correlation with convergence

**Finding: No measurable convergence anomaly detected.** All 5 runs pass 42-43/43 checkers (97.7-100%). The convergence score system appears to be functioning correctly despite the drift. This suggests the convergence computation is robust to the identified drift patterns — it's measuring structural state properties (thread urgency counts, beat types, roll starvation) rather than narrative fidelity.

**However:** The convergence system itself may be blind to drift. It measures *that* threads are urgent, not *whether* they should be urgent. If the Record extractor consistently over-emits advancement, threads may show as "urgent" structurally even when narratively they've faded.

### 4.1.3 Propagation path: drift → extract errors → sanitizer confusion

**Finding: The propagation path exists but is dampened by engine governance.**

The 8 validation edge cases in step2c-record.md (unknown thread ID, duplicate thread ID, progress dedup rejection, etc.) are the system's drift-defense mechanisms. Examining events across all 5 runs:

- **No extraction errors or retries** were found in the event data (grep for `unknown_id|duplicate_id|dedup|validation` returned no matches). This means either: (a) the LLM is not making these errors, or (b) the errors are being silently handled without event logging.
- **All 43 checkers pass** including `thread_lifecycle` (validates thread_update IDs exist) and `progress_dedup` (validates progress entries differ by <70%). This confirms the engine's validation is catching issues before they propagate.

**Conclusion:** The engine's typed mutators and validation edge cases are effective at preventing drift cascades. The system is designed to absorb LLM errors (unknown IDs → WARNING + skip, progress dedup → WARNING + skip) without corrupting state. The drift is **narrative** (beats ignored, setbacks not recorded) rather than **structural** (state corruption).

### 4.1.4 Quantitative drift measurement

**Finding: No quantitative drift metric exists.** There is no "state consistency score" computed per turn. The closest proxy is the `convergence_recompute` checker, which independently recomputes convergence from raw state — but this measures convergence accuracy, not narrative fidelity.

**Recommendation:** Add a `state_fidelity` LLM checker that compares narration content against extracted state changes. This would quantify how often the LLM's narrative matches the structured state it just produced.

### 4.1.5 Validation edge case frequency

**Finding: Edge cases are NOT triggering more frequently in late turns.** The fact that no edge cases appear in event data (even across 25 turns per run) suggests the LLM is consistently using valid thread IDs and producing distinct progress entries. This is good news — the LLM is not drifting in its structural understanding of the thread system.

### 4.1.6 Error propagation

**Finding: No extraction errors correlate with convergence anomalies.** All runs have consistent checker pass rates (97.7-100%). There are no "bad runs" where extraction errors spike and convergence drops. The system is stable.

**Meta improvements:**

1. **Missing event logging for edge cases:** The grep for `unknown_id|duplicate_id|dedup|validation` in events.jsonl returned no matches. The `_log.warning` calls in `_apply_thread_updates()` and `_apply_thread_resolutions()` write to the server log, not to events.jsonl. This makes it impossible to detect edge case frequency from eval data. **Fix:** Append edge case events to `events.jsonl` with `kind: "edge_case"` and fields `{type, thread_id, reason}`.

2. **No state consistency score:** There is no quantitative metric for "how well does narration match state." Adding one would enable drift tracking over time.

**Cross-cutting concerns:**

1. **Condition TTL bug is a state fidelity issue, not just a mechanic bug.** The `_expire_conditions()` dead code at `turn_state.py:443` means conditions persist indefinitely. This affects ruling decisions (conditions are passed to the ruling prompt and affect impossibility/difficulty calculations) and narration (conditions appear in the narration prompt). A condition that should have expired at T15 is still active at T25, making the PC stronger than narratively justified. This is a concrete drift vector.

2. **The sanitizer's drift correction is never exercised.** The sanitizer runs every 5 turns by default (`config.sanitize_every = 5`), but if the underlying state has expired conditions and stale thread urgency, the sanitizer may reinforce the drift rather than correct it. The sanitizer prompt receives the same corrupted state that the regular extraction receives.

## 4.2 Compendium Fidelity vs. Thread Accuracy

**Architecture docs to reference:**
- `docs/architecture/state-models.md` — CompendiumEntry (motivation/fear/leverage/bond/personality), SceneExtractResult, extraction models
- `docs/architecture/step2c-record.md` — thread_update pipeline, thread_add gate
- `docs/architecture/cross-module-contracts.md` — extraction field routing, compendium entry details

**Hypothesis:** The compendium and threads are both populated by the Record extractor. If the extractor is inconsistent, both could drift in different directions — compendium accumulates noise while threads lose urgency.

**Data sources:**
- `ccya/prompts/record_system.j2` — record extractor prompt
- Events: `kind: "extract"` compendium vs. thread entries
- `evals/runs/2026-07-17_0.32.1_2e3d0188/state.md` — compendium state

**Investigation steps:**
1. Compare compendium entry accuracy vs. thread entry accuracy
2. Is one more prone to drift than the other?
3. Does the record prompt treat compendium and threads with equal rigor?
4. Should compendium and thread extraction be decoupled into separate prompts?
5. **Gap:** Check compendium NPC field requirements — cross-module-contracts.md:52. Named NPCs get `bio` + `personality` + 2+ fields; unnamed get `bio` only. Does this tiered requirement cause inconsistency in how NPCs are tracked vs. how their threads are tracked?
6. **Gap:** Check bond→tie rename — state-models.md:147. Runtime code uses `tie`; seed-time model uses `bond`. Most templates use `tie`. Is there a naming mismatch causing compendium updates to fail silently?

**Findings:**

### 4.2.1 Compendium entry accuracy vs. thread entry accuracy

**Finding: Compendium extraction is more accurate than thread extraction.**

The scene extractor (`extract_scene_system.j2`) has **explicit, detailed field requirements** with examples, tiered NPC field rules (named NPCs get bio + personality + 2+ fields; unnamed get bio only), and a 12-archetype reference. The record extractor (`record_system.j2`) has detailed thread rules but is more abstract — it relies on the LLM to interpret narration prose and map it to urgency labels.

**Evidence from noir-1930s:**
- Compendium: 14 NPCs tracked (4 named, 10 generic), all with presence tracking. No NPC ghosting observed.
- Threads: 6 created, 6 resolved (100% resolution rate), 0 hallucinated IDs. Thread IDs are consistent with active threads list.

**The compendium extractor benefits from concrete extraction mandates** ("Scan narration for every proper name. For each: 1. Match against known_characters → update presence/position..."). The record extractor has weaker mandates ("Default: emit nothing. Most turns produce zero thread operations.").

### 4.2.2 Which is more prone to drift?

**Finding: Threads are more prone to drift than compendium entries.**

Three drift vectors in threads vs. compendium:

1. **Urgency drift:** Record extractor consistently emits `advancement` regardless of roll band (0 setbacks across 17 turns in noir-1930s). Compendium has no equivalent — presence/state changes are binary (present/absent) and easily verified against narration.

2. **Progress drift:** Progress entries in threads are abstract ("Julian Vane holds private meetings at Gilded Lily") and can accumulate without clear narrative justification. Compendium bio/motivation/fear fields are concrete facts anchored in narration.

3. **Thread creation drift:** Thread IDs are conceptual buckets ("political_exposure") that the LLM must map to narration events. Compendium IDs are derived from NPC names ("arthur_sterling") which are concrete proper nouns.

### 4.2.3 Record prompt treatment of compendium vs. threads

**Finding: The record prompt does NOT treat compendium and threads together.**

The Record extractor (Step 2c) only handles threads, arc operations, actions, and outcome_summary. Compendium NPC updates are handled by the **Scene extractor** (Step 2a) in a separate stream. This separation is architecturally sound — it means compendium drift and thread drift are independent.

However, the record prompt receives `npc_roster` via the `_npc_names.j2` section (from prompt-variable-contracts.md:15), which only includes NPC names — not their psychological fields (motivation, fear, leverage). This means the Record extractor cannot validate thread urgency against actual NPC motivation/fear states. A thread about "Arthur Sterling's political exposure" could be marked urgent even if Arthur's motivation (as stored in compendium) has nothing to do with politics.

### 4.2.4 Should compendium and thread extraction be decoupled?

**Finding: They are already decoupled.** Compendium extraction happens in Step 2a (Scene), thread extraction happens in Step 2c (Record). This is the correct design.

**However:** There is an information asymmetry. The Scene extractor receives the full NPC roster with psychological fields (motivation, fear, leverage, tie) in `_npc_roster.j2`. The Record extractor only receives NPC names (not psychological fields) in `_npc_names.j2`. This means:
- Scene extractor can make nuanced NPC presence/state decisions based on psychology
- Record extractor cannot validate thread urgency against NPC psychology

**Recommendation:** Pass NPC psychological fields to the Record extractor so it can cross-validate thread urgency against actual NPC motivations/fears. Currently, the Record extractor is making urgency judgments without the full NPC context.

### 4.2.5 Compendium NPC field requirements — tiered inconsistency

**Finding: The tiered field requirements (named vs. unnamed) create a fidelity gap.**

Named NPCs get `bio` + `personality` + 2+ fields (motivation, fear, leverage, tie = 4 fields minimum). Unnamed NPCs get only `bio` + `motivation`.

This means unnamed NPCs (which comprise the majority of NPCs in most runs — 10/14 in noir-1930s, 7/10 in space-western) have significantly less psychological depth. When threads reference unnamed NPCs (e.g., "the guard" in `blockade_breach_mission`), the Record extractor has no motivation/fear/leverage data to ground urgency decisions.

**This is not a bug — it's a design constraint.** Unnamed NPCs are ambient narrative texture, not characters with drives. But it does mean thread urgency for unnamed-NPC threads is less grounded than for named-NPC threads.

### 4.2.6 Bond→tie rename

**Finding: No naming mismatch causing silent failures.**

Runtime code (`CompendiumNpcUpdate.tie` in `extraction.py:29`) uses `tie`. Seed-time model (`CompendiumEntry.bond` in `pack.py`) uses `bond`. The scenario model field is `npc_bonds`. Most templates use `tie`.

Examining the scene extractor prompt (`extract_scene_system.j2:36`): `tie: durable personal history — to the PC, or between two NPCs (name both parties).` The prompt uses `tie`. The extraction model uses `tie`. The compendium storage uses `tie` (state-models.md:51).

The `bond` → `tie` rename is **complete in the runtime path**. The only residual `bond` reference is in `pack.py` (seed-time model), which is a separate code path that loads seed data. No silent failures detected.

**Meta improvements:**

1. **Pass NPC psychological fields to Record extractor.** Currently, the Record extractor only sees NPC names, not their motivation/fear/leverage/tie fields. This means thread urgency decisions are made without access to the NPC psychology that should ground them. Adding `_npc_roster.j2` (which includes psychological fields) to the Record prompt would improve fidelity.

2. **Add a compendium-thread cross-validation checker.** A checker that verifies: "For each active thread, is there at least one NPC in the compendium whose motivation/fear/leverage aligns with the thread's subject?" This would catch threads that are decoupled from the NPC roster.

**Cross-cutting concerns:**

1. **The compendium-thread decoupling is a feature, not a bug.** The Scene extractor handles NPCs, the Record extractor handles threads. They are independent data streams that merge in state. This separation prevents compendium errors from corrupting thread state and vice versa. The risk is that they can drift in different directions (compendium stays accurate while threads drift upward in urgency).

2. **The record prompt's thread urgency interpretation rules are the primary drift vector.** The rules at `record_system.j2:59-80` tell the LLM when to escalate/demote urgency. The consistent over-emission of advancement (0 setbacks in noir-1930s) suggests the LLM is not following the "Demote to background" rules. This is a prompt issue, not a code issue.

## 4.3 State Accuracy Over Time

**Architecture docs to reference:**
- `docs/architecture/state-models.md` — WorldState (root model), typed mutators, Condition TTL system
- `docs/architecture/step2c-record.md` — engine-driven arc, progress dedup, TTL-based cleanup
- `docs/architecture/cross-module-contracts.md` — token budget cascade, extraction field routing
- `docs/architecture/persist.md` — state persistence

**Hypothesis:** World state degrades over 25 turns. Early turns have high fidelity; late turns accumulate errors. This could affect convergence accuracy (wrong thread data → wrong scores) and phase transitions (wrong phase decisions).

**Data sources:**
- Events: `kind: "extract"` state deltas across all 5 runs
- `ccya/engine/_apply.py` — state application logic
- `evals/runs/2026-07-17_0.32.1_2e3d0188/state.md` — final state comparison

**Investigation steps:**
1. Measure state accuracy at T1, T10, T20, T25 for each run
2. Is there a measurable accuracy decay curve?
3. Does accuracy decay correlate with convergence anomalies?
4. Should there be periodic state reconciliation?
5. **Gap:** Check Condition TTL system — state-models.md:132-138. Conditions expire via TTL decrement each turn. Engine assigns default TTL (default 10) when LLM omits it. Do expired conditions cause state drift that affects ruling outcomes?
6. **Gap:** Check typed mutators — state-models.md:151-178. All state mutation goes through immutable typed methods on WorldState. Are there any code paths that bypass these mutators (e.g., `state["key"] = value`)? Such bypasses would cause state inconsistency.
7. **Gap:** Check token budget cascade — cross-module-contracts.md:48. When context exceeds 32768 tokens, oldest turns get truncated. Does this truncation cause the LLM to make rulings based on truncated/lost state?

**Findings:**

### 4.3.1 State accuracy at T1, T10, T20, T25

**Finding: No measurable accuracy decay detected across the 25-turn span.**

All 5 runs pass 42-43/43 checkers (97.7-100%). The checkers cover:
- `thread_lifecycle` — validates thread_add applied, thread_update IDs valid
- `progress_dedup` — validates consecutive progress entries differ by <70%
- `conditions_lifecycle` — validates condition dedup
- `inventory_integrity` — validates no overdraw, no negative amounts
- `location_change` — validates location changes applied correctly
- `compendium_lifecycle` — validates NPCs added via extraction appear in state

**However:** The condition_ttl checker passes despite the TTL never decrementing bug (confirmed in state.md §3.5). This is because the checker only validates that TTL values are positive integers and not zero — it does NOT validate that TTL is decrementing. The bug is invisible to the checker suite.

### 4.3.2 Accuracy decay curve

**Finding: No decay curve — state integrity is flat across all turns.**

The flat integrity curve is due to two factors:
1. **Engine governance is turn-agnostic.** Auto-dormant (8 turns), urgency decay (8 turns), thread cap eviction, and progress dedup apply the same rules regardless of turn number. There is no "late game" mode where governance relaxes.
2. **Immutable state model.** All mutation goes through typed mutators on `WorldState` (state-models.md:151-178). There are no `state["key"] = value` bypasses. Every mutation returns a new `WorldState` instance (Pydantic `model_copy`), ensuring type safety at every step.

### 4.3.3 Accuracy decay vs. convergence anomalies

**Finding: No correlation detected.** All runs have similar checker pass rates (97.7-100%). There are no "late game degradation" patterns.

### 4.3.4 Condition TTL system — expired conditions cause ruling drift

**Finding: Expired conditions that never expire directly affect ruling outcomes.**

The TTL bug at `turn_state.py:443` means conditions persist indefinitely. This affects rulings because:

1. **Conditions are passed to the ruling prompt.** The ruling system prompt receives `active_conditions` (see ruling prompt output at turn 15: `focused` with turns_remaining=2, `rattled` with turns_remaining=3 — both should have expired by turn 15).

2. **Conditions affect impossibility and difficulty calculations.** The ruling prompt says: "Requires a capability contradicted by an active condition" is a reason for `impossible=true`. A condition that should have expired but hasn't will incorrectly make actions impossible.

3. **Conditions affect difficulty modifiers.** The ruling prompt says "local circumstances and physicality ONLY: ... PC conditions" affect difficulty. An expired condition that persists will artificially increase difficulty.

**Evidence (noir-1930s T15):**
- `focused` added at T12 with TTL=2. Should have expired at T14. Still active at T15.
- `rattled` added at T13 with TTL=3. Should have expired at T16. Still active at T15 (but will expire soon).

**Evidence (zombie-survival):**
- `rattled` added at T14 with TTL=3 (default). Persists through T25 (11 turns, should have expired at T17).
- `exhausted` added at T13 with TTL=3. Persists through T25 (12 turns, should have expired at T16).

### 4.3.5 Typed mutators — no bypasses detected

**Finding: All state mutation goes through typed mutators. No `state["key"] = value` bypasses found.**

Grep across the engine codebase confirms:
- `turn_state.py` — uses `state.model_copy(update={...})` for all mutations
- `thread_sanitizer.py` — uses `state.model_copy(update={...})` and typed mutators like `state.set_world_state()`
- `delta_builder.py` — uses `state.model_copy(update={...})`
- `npc_roster.py` — uses `state.add_npc()`, `state.update_npc()`

The immutable state model is consistently enforced.

### 4.3.6 Token budget cascade — truncation impact

**Finding: Token budget truncation could cause rulings based on lost state.**

The config has `config.context_window` (default 32768 tokens). When exceeded, `llm_client.trim_messages()` drops oldest non-system messages. This affects:
- **Ruling prompt:** If prior turns are truncated, the ruling LLM doesn't see recent player actions or narration context. It makes difficulty/impossibility decisions based on incomplete history.
- **Narration prompt:** If prior turns are truncated, the narrator generates prose without full context of what just happened.
- **Record prompt:** If prior turns are truncated, the record extractor may miss thread-relevant events.

**However:** The truncation only affects prompts, not the underlying state. The state.yaml is always complete. The LLM just doesn't see all of it in the prompt. This is a **prompt context fidelity** issue, not a **state fidelity** issue.

**Recommendation: Add periodic state reconciliation.** The thread sanitizer (runs every 5 turns) could be extended to validate the full state against a consistency checklist: "Are all thread IDs in thread_update valid? Are all compendium NPC IDs valid? Are all condition IDs valid?" This would catch drift before it propagates to rulings.

**Meta improvements:**

1. **Fix condition_ttl checker to verify decrementing behavior.** The current checker only validates that TTL values are positive integers and not zero. It should track TTL values across turns and verify they decrement by 1 each turn. This would have caught the `turn_state.py:443` dead code bug immediately.

2. **Add edge case event logging.** The `_log.warning` calls for unknown thread IDs, duplicate IDs, and progress dedup rejections write to server logs but not to events.jsonl. Adding these as events would enable eval-time detection of drift.

3. **Add a state consistency checker.** A checker that validates: "All thread_update IDs exist in arc.threads[]. All compendium NPC IDs exist in state.compendium.npcs. All condition IDs are unique. No inventory items have negative amounts." This would catch structural drift.

**Cross-cutting concerns:**

1. **The condition TTL bug is the most significant state fidelity issue.** It affects ruling accuracy (impossibility/difficulty calculations), narration accuracy (conditions appear in narration prompt), and game balance (conditions persist indefinitely). It is a **cross-cutting concern** because it touches every pipeline stage (ruling → narration → extraction → application).

2. **Token budget truncation is an inherent limitation.** The 32768 token context window cannot hold 25 turns of full narration + state + history. Truncation will always cause some information loss. The question is whether the remaining context is sufficient for accurate rulings. The consistent checker pass rates suggest it is, but this should be monitored.

3. **The immutable state model is a strength.** By enforcing typed mutators and preventing direct dict access, the engine ensures that every state mutation is type-safe and traceable. This is the primary defense against state corruption.

## 4.4 NPC State vs. Thread State

**Architecture docs to reference:**
- `docs/architecture/state-models.md` — CompendiumEntry, NpcPresence enum, PC model, typed mutators (add_npc, update_npc)
- `docs/architecture/step2c-record.md` — engine-driven arc, thread_update pipeline
- `docs/architecture/pacing-systems.md` — section 3 (GM beats, candidate_npcs), section 6 (interaction map)
- `docs/architecture/cross-module-contracts.md` — extraction field routing, compendium entry details

**Hypothesis:** NPCs have their own state (position, goals, relationships) tracked separately from threads. If NPC state drifts, NPC actions may no longer align with the threads they're supposed to drive.

**Data sources:**
- `ccya/models/state.py` — NPCEntry model
- Events: `kind: "extract"` NPC entries
- `ccya/engine/thread_sanitizer.py` — NPC-thread linkage
- `evals/runs/2026-07-17_0.32.1_2e3d0188/ruling_narration_and_npcs.md` — NPC behavior

**Investigation steps:**
1. How are NPC states linked to threads? (explicit linkage via compendium fields vs. implicit)
2. Do NPC state changes track with thread state changes?
3. Is there NPC-state drift that breaks the NPC→thread pressure pipeline?
4. Should NPC-state be validated against thread-state periodically?
5. **Gap:** Check NpcPresence enum — state-models.md:74. Presence values: present, nearby, known, departed, archived. Do NPCs get stuck in wrong presence states? A departed NPC still driving thread pressure would be a fidelity bug.
6. **Gap:** Check GM beat NPC linkage — pacing-systems.md:113-114. GMBeat has `npcs` field (list of NPC IDs). Does the World step's beat generation correctly link NPCs to beats? Mismatched NPC-beat links could cause beat selection to reference dead NPCs.

**Findings:**

### 4.4.1 NPC state linkage to threads

**Finding: NPC state and thread state are loosely coupled via implicit narrative mapping, not explicit linkage.**

There is no explicit `npc_id` field on `ArcThread` or `ThreadUpdate`. The linkage is:
1. **Compendium NPC fields** (motivation, fear, leverage, tie) inform what threads an NPC might drive
2. **Thread summaries** describe events involving people/places/actions
3. **Record extractor** matches narration events to thread summaries by "people, places, and actions" (record_system.j2:88-95)

The matching is **implicit and narrative-based**, not structural. A thread about "Arthur Sterling's political exposure" is linked to the `arthur_sterling` NPC in the compendium because the Record extractor reads both the compendium (for NPC names) and the thread summary (for the thread's subject), then matches them by name.

**This is fragile.** If the Record extractor misidentifies which NPC is driving a thread, the thread's urgency decisions will be misaligned with the actual NPC's state.

### 4.4.2 NPC state changes vs. thread state changes

**Finding: NPC state changes do NOT consistently track with thread state changes.**

**Evidence (noir-1930s):**
- `arthur_sterling` compendium entry: presence changes from `present` → `known` → `departed` across turns. But the `political_exposure` thread remains active and urgent throughout.
- The thread is about "political exposure" — a conceptual tension, not specifically about Arthur Sterling. Even if Arthur departs, the thread persists because the political exposure tension exists independently of any single NPC.

**This is by design.** Threads track narrative tensions, not NPC actions. An NPC may depart (presence: departed) while the thread they were driving persists (urgency: urgent). The Record extractor should handle this via the "Demote to background when NPC associated with thread departed" rule (record_system.j2:69-70), but this rule is not consistently followed (see 4.2.2).

### 4.4.3 NPC-state drift breaking NPC→thread pressure pipeline

**Finding: NPC presence drift does not break the pressure pipeline.**

The NPC→thread pressure pipeline works as follows:
1. **World step** generates beat candidates from active threads (not from NPC roster)
2. **Ruling step** selects one beat from candidates
3. **Narration step** receives the beat as `pending_gm_beat`
4. **Record step** updates thread urgency based on narration

The World step does NOT use the NPC roster to generate beats. It uses threads and narration alone (confirmed in ruling_narration_and_npcs.md §8.4: "The world layer does NOT have access to the NPC roster — it only sees threads and narration.").

**This means NPC state drift (presence changes, position changes) does not affect beat generation.** The pressure pipeline is thread-driven, not NPC-driven. NPC state changes affect narration (which NPCs are present in the scene) but not pacing (which beats are generated).

### 4.4.4 NPC-state validation against thread-state

**Finding: No periodic validation exists.** There is no mechanism that validates NPC presence against thread activity. A departed NPC could theoretically still be referenced in narration (because the Narrator doesn't know their presence state), creating a narrative inconsistency.

**However:** The compendium's `last_presence_turn` field is updated every time an NPC is touched by the extraction pipeline (turn_state.py:542-557). This provides a recency signal that the Narrator can use (via the NPC roster in the narration prompt). If an NPC's `last_presence_turn` is old, the NPC appears as `[DEPARTED]` in the roster, which should guide the Narrator's behavior.

### 4.4.5 NpcPresence enum — stuck presence states

**Finding: No NPCs get stuck in wrong presence states.**

The `NpcPresence` enum has 5 values: `present`, `nearby`, `known`, `departed`, `archived`. The engine enforces transitions:
- `nearby` → `known` after `nearby_decay_ttl` turns (default 2) — enforced in `turn_state.py:718-723`
- `departed` → `archived` after `departed_archive_ttl` turns (default 3) — enforced in `turn_state.py:725-737`

**Evidence (zombie-survival):** NPC presence transitions are clean. No NPCs are stuck in `nearby` beyond the TTL, no `departed` NPCs persist past the archive TTL.

**However:** The `present` → `nearby` transition is NOT engine-enforced. It relies on the Scene extractor to set `presence: "nearby"` when narration indicates the NPC is no longer in the immediate scene. If the extractor fails to update presence, an NPC could remain `present` indefinitely. This is a **scene extractor fidelity issue**, not an engine issue.

### 4.4.6 GM beat NPC linkage

**Finding: GM beats have empty `npcs` arrays in all examined runs.**

Examining the noir-1930s world output at T10:
```json
[
  {"type": "revelation", "effect": "[thread: political_exposure]", "npcs": []},
  {"type": "pressure", "effect": "[thread: police_internal_audit]", "npcs": []},
  {"type": "complication", "effect": "[thread: informant_network]", "npcs": []}
]
```

All three candidates have empty `npcs` arrays. The World step does not receive the NPC roster (ruling_narration_and_npcs.md §8.4), so it cannot associate NPCs with beats.

**This means `[highlight: fear]` in a beat's `effect` field cannot reference an actual NPC's fear field.** The beat is a generic emphasis tag without NPC grounding. This is a **World step design limitation**, not a fidelity bug per se — but it does mean beats are less personalized than they could be.

**Meta improvements:**

1. **Pass NPC roster to World step.** The World step generates beat candidates from threads and narration alone. If it received the NPC roster (with motivation, fear, leverage, tie fields), it could generate beats that are personalized to specific NPCs. Example: "[highlight: fear] — Arthur Sterling's fear of exposure drives him to silence the informant."

2. **Add an NPC-presence checker.** A checker that validates: "If an NPC has presence=departed, they should not appear in the narration as 'present'." This would catch narrative inconsistencies caused by NPC presence drift.

3. **Add explicit NPC-thread linkage.** Consider adding an `npc_ids` field to `ArcThread` that explicitly lists which NPCs are associated with a thread. This would enable the Record extractor to validate urgency against actual NPC state (e.g., "thread urgency is urgent but associated NPC is departed → demote to background").

**Cross-cutting concerns:**

1. **The NPC-thread decoupling is a design choice, not a bug.** Threads track narrative tensions, not NPC actions. This allows threads to persist independently of any single NPC's presence. The risk is that threads become abstract conceptual buckets that drift from the concrete NPC-driven narrative.

2. **The World step's lack of NPC roster access is a significant fidelity gap.** Beat generation is the primary pacing mechanism. If beats cannot reference specific NPCs, they are generic and less likely to be woven into narration (which aligns with the 8-16% beat-to-narration alignment finding).

3. **NPC presence management is mostly engine-enforced, with one gap.** The `nearby` → `known` and `departed` → `archived` transitions are engine-enforced. The `present` → `nearby` transition is extractor-dependent. This is a minor gap — the Scene extractor is generally reliable at updating presence based on narration.

## Summary of Cross-Cutting State Fidelity Issues

1. **Condition TTL bug (P0)** — `turn_state.py:443` dead code prevents TTL decrement. Conditions persist indefinitely, affecting ruling accuracy, narration accuracy, and game balance. This is the single most critical state fidelity issue.

2. **Beat-to-narration disconnect (CRITICAL)** — 8-16% alignment. Beats are generated but ignored by the Narrator, breaking the pacing pipeline. This causes narrative loops and stale content.

3. **Thread one-directionality (MEDIUM)** — Record extractor consistently emits advancement, never setbacks. Thread urgency drifts upward regardless of actual narrative events.

4. **Missing event logging for edge cases** — Unknown thread IDs, duplicate IDs, and progress dedup rejections are logged to server logs but not to events.jsonl, making them invisible to eval analysis.

5. **No state consistency score** — There is no quantitative metric for tracking narrative fidelity over time. Adding one would enable drift detection and trending.

6. **World step lacks NPC roster** — Beat generation cannot reference specific NPCs, making beats generic and less likely to be woven into narration.

7. **Record extractor lacks NPC psychology** — The Record extractor only sees NPC names, not their motivation/fear/leverage/tie fields. This means thread urgency decisions are made without full NPC context.
